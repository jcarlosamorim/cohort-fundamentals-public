Encontro 5 • Por Que PRD E a Alma

Receita completa vs "coloca farinha e da um jeito".
A diferenca entre um projeto que funciona e um que morre.

Todo projeto que falha tem algo em comum: comecou sem um PRD decente. Aqui voce vai ver, lado a lado, o que separa um documento que guia do caos total.

O Padrao Ouro

10 Secoes de um PRD Que Funciona

Um PRD bom responde TODAS as perguntas antes que alguem precise perguntar. Veja as secoes obrigatorias do template AIOS.

1
Problem Statement
Qual dor resolve? Para quem? Se voce nao sabe responder isso em 1 frase, o projeto ja comecou errado.
2
Solution Overview
O que o sistema faz em 1 paragrafo. Se precisa de 3 paginas pra explicar, o escopo esta grande demais.
3
User Persona / ICP
Quem vai usar? Idade, dor, desejo. Quanto mais especifico, melhor o Claude entende o contexto.
4
Functional Requirements (FRs)
Lista de TUDO que o sistema FAZ. Cada FR vira uma task de desenvolvimento. Sem FRs = sem roadmap.
5
Non-Functional Requirements (NFRs)
Performance, seguranca, limites. O sistema funciona, mas aguenta 1000 usuarios ao mesmo tempo?
6
Scope IN / OUT
O que FAZ parte e o que NAO faz. O Scope OUT e tao importante quanto o IN — ele impede feature creep.
7
Tech Stack
Quais tecnologias e por que. "Next.js porque precisa de SSR para SEO" — nao "Next.js porque todo mundo usa".
8
Integrations
APIs externas, tokens, autenticacao. Cada integracao precisa de: endpoint, auth method, rate limit, fallback.
9
Data Model
Que dados armazena e onde. Tabelas, campos, relacoes. Sem isso, o banco muda 5 vezes durante o dev.
10
Success Metrics
Como saber se deu certo? Numeros concretos: "50 leads/dia", "tempo de resposta < 200ms", "NPS > 8".
Exemplo Real: Prospect Hunter
Problem Statement
Prospectar clientes manualmente consome 4h/dia e gera leads desqualificados. O processo atual depende de busca manual no Instagram, sem criterio de qualificacao.
User Persona / ICP
Dono de agencia digital, 25-45 anos, fatura 20-100k/mes, precisa de leads B2B qualificados, nao tem equipe de SDR dedicada.
Integration
Apify API (token auth), Actor: apify/instagram-scraper
Rate limit: 100 requests/hora | Fallback: retry com backoff exponencial
O Anti-Padrao

Quando o PRD Mata o Projeto

Um PRD ruim e pior que nenhum PRD — ele da a ilusao de planejamento enquanto esconde buracos fatais.

Problem Statement VAGO
"Quero um app legal"
Nao define a dor, nao define o publico, nao define o resultado esperado. O Claude vai inventar tudo.
User Persona / ICP GENERICO
"Todo mundo"
Quem e "todo mundo"? Quando voce constroi pra todos, nao resolve o problema de ninguem.
Functional Requirements CIRCULAR
"O app faz tudo que precisa"
Isso nao diz NADA. O que e "tudo"? Sem lista explicita, cada pessoa entende diferente. O Claude tambem.
Scope AUSENTE
(Nao definido)
Sem scope, o projeto cresce infinitamente. O Claude vai adicionar features que voce nao pediu. E voce nao vai saber onde parar.
Tech Stack DELEGADO
"O que o Claude escolher"
Voce esta deixando o Claude decidir a arquitetura do SEU projeto. Ele pode escolher algo que voce nao sabe manter.
Integrations ADIADO
"Depois a gente ve"
Quando "depois" chegar, voce descobre que precisa de token, auth, rate limit, e o codigo inteiro precisa mudar.
A Comparacao

Prospect Hunter: Bom vs Ruim

O mesmo projeto. Duas abordagens. Resultados completamente diferentes.

PRD Ruim
prd-ruim.md
# Prospect Hunter
 
Quero um sistema que busca
leads no Instagram.
 
Usa Apify pra isso.
 
Salva os dados em algum lugar.
3 linhas. Zero detalhe de auth, data model, scope, persona. O Claude vai adivinhar tudo.
PRD Bom
prd-bom.md
# Prospect Hunter
 
## Problem
Prospectar clientes B2B
manualmente consome 4h/dia...
 
## ICP
Donos de agencias digitais,
25-45 anos, 20-100k/mes...
 
## Integrations
- Apify: Actor instagram-scraper
- Auth: API Token via env APIFY_TOKEN
- Rate limit: 100 req/hora
 
## Data Model
- leads: name, handle, followers,
  bio, email, score
Cada decisao ja tomada. O Claude sabe exatamente o que construir, com que, e os limites.
Por Que Isso Importa
O PRD ruim tem 3 linhas e parece rapido. O PRD bom tem 47 decisoes e parece trabalhoso. Mas o ruim gera 20 horas de retrabalho. O bom gera um projeto que funciona de primeira. O trabalho e o mesmo — a questao e QUANDO voce faz.
Os Erros

7 Erros Que Matam Projetos Antes de Comecar

Se voce reconhecer algum desses no seu projeto, pare e conserte ANTES de escrever codigo.

1 FATAL
Sem persona definida
Voce constroi pra ninguem. Sem saber QUEM usa, toda decisao de UX, copy e funcionalidade e um chute no escuro.
2 FATAL
Scope infinito
O projeto nunca termina. Sem Scope OUT, cada "e se a gente adicionasse..." vira uma nova feature. O projeto cresce ate morrer.
3 CRITICO
Sem NFRs
Funciona no teste, quebra em producao. Sem limites de performance, seguranca e escalabilidade, voce so descobre o problema quando esta ao vivo.
4 CRITICO
Integracoes vagas
Descobre na hora que precisa de token, auth, rate limit. O dev para no meio do codigo pra pesquisar API docs. Horas perdidas.
5 ALTO
Requisitos ambiguos
Cada pessoa entende diferente. "O sistema deve ser rapido" — rapido e 100ms ou 5s? Sem numero, sem acordo.
6 ALTO
Sem success metrics
Nunca sabe se deu certo. O projeto "termina" mas ninguem sabe se atingiu o objetivo. Sem metrica, sem aprendizado.
7 MEDIO
Sem data model
Muda o banco 5 vezes. Sem definir tabelas e campos antes, cada nova feature reestrutura tudo. Migracao vira pesadelo.

Insight da Aula

O PRD nao e burocracia. E a diferenca entre pedir "faz um app" e entregar um blueprint com 47 decisoes ja tomadas.

Cada decisao no PRD e uma decisao que voce NAO precisa tomar durante o desenvolvimento. E uma pergunta que o Claude NAO precisa adivinhar.

Receita completa = prato perfeito.
"Coloca farinha e da um jeito" = desastre garantido.
