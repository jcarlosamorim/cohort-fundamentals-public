O Fluxo do Maker.
Da Ideia ao Deploy.

Voce ja conhece as pecas do AIOS. Agora vai ver como elas se conectam — o caminho completo que um Maker percorre para transformar uma ideia em software funcionando.

O Inicio

O Chef Entrou na Cozinha

O Maker recebeu uma missao: construir algo real. Ele abre o terminal e... para. Porque no AIOS, ate o chef segue uma receita.

Na Cozinha
Um chef de verdade nao improvisa sem receita. Ele tem a ficha tecnica do prato (story), os ingredientes preparados (PRD) e o mise en place (arquitetura). O AIOS e o mise en place do Maker.
Terminal — Sem AIOS vs Com AIOS

Passo 1 de 5

A Story: A Receita do Prato

Antes de cozinhar, o chef precisa da receita. No AIOS, a receita e a Story — um documento que define EXATAMENTE o que construir.

O que uma Story contem
Titulo e descricao — o que sera construido e por que
Acceptance Criteria (AC) — quando considerar PRONTO
Scope IN/OUT — o que FAZ e o que NAO faz parte
Dependencies — o que precisa estar pronto antes
Terminal — @sm criando a Story
voce: @sm Crie a story para autenticacao
 
@sm (River): Usando task create-next-story.md
  → Titulo: Implementar autenticacao email + senha
  → AC: Given usuario na tela / When digita email+senha / Then acessa o dashboard
  → Scope IN: Login, cadastro, recuperar senha
  → Scope OUT: OAuth, 2FA, admin panel
  ✓ docs/stories/1.1.story.md
Por Que Isso Importa
Sem story, o @dev improvisa. Com story, ele executa com precisao. O Scope OUT e tao importante quanto o IN — ele impede que o agente invente funcionalidades que ninguem pediu. Menos desperdicio, mais foco.
Detalhe: @po valida antes do @dev comecar
Depois que o @sm cria, o @po (Pax) faz 10 verificacoes na story. Se estiver incompleta, volta pro @sm. Nenhum @dev comeca a cozinhar com receita mal escrita.
Passo 2 de 5

O @dev Entra: Hora de Cozinhar

Com a receita (story) na mao, o @dev (Dex) entra na cozinha. Ele nao decide O QUE fazer — a story ja definiu. Ele foca em COMO fazer bem.

YOLO
Autonomo. 0-1 prompts. Para stories simples e claras. O chef cozinha sozinho.
Interactive
Guiado. 5-10 prompts. Para aprendizado. O chef pede sua opiniao em cada etapa.
Pre-Flight
Planejado. Todas perguntas antes. Para stories complexas. O chef faz o briefing completo antes de ligar o fogao.
Terminal — @dev implementando
voce: @dev Implemente a story 1.1
 
@dev (Dex): Lendo story...
  → Modo: Interactive (padrao)
  → AC #1: Login email + senha
  → Implementando...
 
@dev: Sugestao: Usar Supabase Auth
voce: Aprovado
 
@dev: ✓ auth.js criado
@dev: ✓ auth-ui.js criado
@dev: ✓ Testes passando (3/3)
@dev: ✓ git commit: "feat: implement auth"
Passo 3 de 5

O @qa Faz a Vistoria: Passa ou Nao Passa

Antes de servir o prato, o inspetor de qualidade verifica. Os 7 checks do QA Gate sao objetivos — nao e opiniao, e criterio.

7 Verificacoes do QA Gate
1. Codigo limpo e legivel
2. Testes unitarios adequados
3. Criterios de aceite atendidos (AC)
4. Sem regressoes
5. Performance aceitavel
6. Seguranca basica (OWASP)
7. Documentacao atualizada
PASS
→ Segue para deploy
CONCERNS
→ Aprovado com observacoes
FAIL
→ Volta para @dev com feedback especifico
E se der FAIL?
O @qa retorna com feedback especifico — nao e "arruma ai". E "o AC #2 nao foi atendido: o botao de recuperar senha nao redireciona". O @dev corrige e submete de novo. Esse loop pode rodar ate 5 vezes antes de escalar.
Na cozinha: O inspetor prova o prato. Se o sal esta errado, nao serve. O chef ajusta e submete de novo. Simples assim.
Passo 4 de 5

O @devops Entrega: No Ar

O @devops (Gage) e o UNICO autorizado a fazer git push. Nenhum outro agente toca no remoto. Ele roda os pre-push gates e faz o deploy.

Terminal — @devops fazendo deploy
@qa (Quinn): QA Gate → PASS (7/7)
 
@devops (Gage): Pre-push quality check...
  → Lint: ✓
  → Types: ✓
  → Tests: ✓
  → git push origin feat/auth
  → Vercel: Building...
  ✓ Deployed: meu-projeto.vercel.app
Regra de Ouro
So o @devops faz push. O @dev faz commit local, mas NUNCA push. Isso protege o codigo em producao — como a construtora que so entrega com habite-se.
Quem pode o que
@dev — git add, commit, branch, stash
@dev — git push, gh pr create
@devops — git push, deploy, CI/CD
@devops — alterar stories, editar AC
✓ = permitido    ✗ = bloqueado    Cada agente fica na sua raia.
Passo 5 de 5

O Story Development Cycle (SDC)

O fluxo completo do Maker em 5 passos. Cada agente tem seu papel. Nenhum faz o trabalho do outro.

1
@sm (River) Cria a story
= A receita do prato
2
@po (Pax) Valida a story (10 checks)
= Aprovacao do cardapio
3
@dev (Dex) Implementa seguindo a story
= O chef cozinha
4
@qa (Quinn) QA Gate: 7 verificacoes
= Vistoria do prato
5
@devops (Gage) Push + deploy
= Serviu na mesa
Status da Story ao Longo do Ciclo
Draft → Ready → InProgress → InReview → Done
Cada agente muda o status ao completar sua etapa. Voce sempre sabe em que ponto a story esta.
O Ciclo que Todo Maker Roda
Este e o ciclo que todo Maker roda no AIOS. Simples, replicavel, com qualidade garantida. Proximo projeto? Mesmo processo. O chef muda o prato, mas a cozinha continua organizada.

Da ideia ao deploy. Com processo.

Story → Validacao → Implementacao → QA Gate → Deploy. Cinco passos. Cinco agentes. Um resultado confiavel.
