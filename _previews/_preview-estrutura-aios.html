Caminho A

Claude Code Sozinho

Voce abre o terminal, digita claude, e pede. O Claude e capaz — o resultado vai ser bom. Mas repara quem esta gerenciando o processo.

Terminal — Claude Code (sem AIOS)
voce: Cria uma landing page para meu curso de fotografia
 
claude: Vou criar! Preciso de alguns detalhes:
  - Qual o publico-alvo?
  - Qual o preco?
  - Tem depoimentos?
  - Qual o diferencial do curso?
 
voce: [responde o que lembra na hora]
 
claude: ✓ Gerei a landing page completa!
  index.html + styles.css + hero + depoimentos + CTA
 
  // Resultado: bom. Mas...
  // Voce lembrou de tudo? Faltou algo no brief?
  // A copy seguiu algum framework ou foi inventada?
  // Alguem validou antes de ir pro ar?
  // No proximo projeto, comeca tudo do zero de novo.
O Que Falta (Nao e Competencia)
⚠ Voce e o gerente de projeto — decide o que pedir, em qual ordem, o que validar
⚠ Sem template de requisitos — o brief depende da sua memoria na hora
⚠ Sem quality gate — quem verifica se a copy ta boa? Se o CTA converte?
⚠ Sem processo replicavel — no proximo projeto, comeca do zero
⚠ Um contexto faz tudo — requisitos, arquitetura, codigo e QA no mesmo fluxo

Na Reforma: Profissional Talentoso Sozinho
Imagine um profissional excelente reformando sua casa. Ele sabe fazer eletrica, encanamento, pintura. E competente. Mas ele decide tudo na hora, sem planta, sem cronograma, sem vistoria formal. O resultado depende da memoria dele naquele dia — e no proximo cliente, comeca tudo de cabeca de novo.
Caminho B

Claude Code + AIOS

O mesmo Claude, o mesmo modelo. Mas agora com processo definido: cada etapa tem um agente especialista, um template, e um quality gate.

Terminal — Claude Code + AIOS (.aios-core/)
voce: @pm Preciso de uma landing page para meu curso de fotografia
 
@pm (Morgan): Seguindo task create-doc.md + template prd-tmpl.yaml
  → Elicitacao estruturada: publico, dor, oferta, metricas, concorrentes
  → PRD completo gerado (nada esquecido — o template garante)
  ✓ docs/prd/landing-fotografia.md
 
voce: @architect Projeta a arquitetura
@architect (Aria): Analisando PRD → front-end-architecture-tmpl.yaml
  → Tech stack definida, estrutura documentada
  ✓ Decisoes tecnicas registradas
 
voce: @dev Implementa
@dev (Dex): Seguindo dev-develop-story.md + arquitetura
  ✓ Landing page implementada
 
@qa (Quinn): qa-gate.md → 7 checks objetivos
  ✓ QA Gate: PASS (7/7)
 
@devops (Gage): Pre-push quality gates → deploy
  ✓ Deployed: landing-fotografia.vercel.app
 
  // Proximo projeto? Mesmo processo. Mesmos templates.
  // Nada esquecido. Qualidade verificada. Replicavel.
O Fluxo: Quem Faz o Que
1
@pm (Morgan) = Engenheiro da Obra
Coleta requisitos com elicitacao estruturada — o template prd-tmpl.yaml garante que nada e esquecido. Publico, dor, oferta, metricas, concorrentes. Tudo documentado.
2
@architect (Aria) = Arquiteta
Analisa o PRD e define a arquitetura tecnica usando front-end-architecture-tmpl.yaml. Tech stack, estrutura, componentes — decisoes documentadas, nao improvisadas.
3
@dev (Dex) = Mestre de Obras
Segue dev-develop-story.md passo a passo. Recebe o PRD + arquitetura prontos — nao precisa inventar requisitos. Foco total em implementar bem.
4
@qa (Quinn) = Inspetor de Qualidade
Executa qa-gate.md com 7 verificacoes objetivas: codigo, testes, criterios de aceite, regressao, performance, seguranca, docs. Passa ou nao passa.
5
@devops (Gage) = Entrega & Habite-se
Roda pre-push quality gates, cria PR, faz deploy. Unico agente autorizado a fazer git push — nenhum outro toca no remoto.
🏗️
Na Reforma: Construtora Organizada
Agora imagine uma construtora. O engenheiro (@pm) faz a planta completa. A arquiteta (@architect) define a estrutura. O mestre de obras (@dev) executa seguindo o projeto. O inspetor (@qa) faz a vistoria formal. E a construtora (@devops) entrega com habite-se. O profissional e o mesmo — o que muda e o processo.
A Estrutura

Reforma ↔ .aios-core/

Cada peca de uma construtora organizada tem um equivalente direto no .aios-core/:

O Sonho dos Tokens
Quando o Claude sabe quem ele e (agent), o que fazer (task), como fazer (template) e quando parar (checklist) — cada token vai direto pro resultado. Sem gastar tokens decidindo o processo. O processo ja esta decidido.
